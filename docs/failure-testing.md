# Process failure tests

`tests/process_failure.rs` runs the compiled server and replica as separate operating-system processes on loopback ports and distinct real data directories. It writes a known key sequence, kills the replica while the primary is streaming writes to it, restarts it and waits for its durable applied LSN to catch up. It then kills the primary while a client is writing, restarts it, and checks that every acknowledged write survived (at most the single in-flight write may additionally be present). Finally it writes again, waits for the replica to converge and checks the replica's recovered on-disk state after both processes stop.

A second test in the same file runs the SOW §19 example at full size. It writes 100,000 records from 16 concurrent clients through a primary with one replica, and kills the primary once 50,000 to 90,000 writes have been acknowledged. After the restart, every acknowledged key must be readable, and the recovered LSN must lie between the acknowledged count and that count plus one in-flight write per client. The test then writes the remaining records, waits for the replica, and compares both nodes' on-disk state: 100,000 keys, the same last LSN, and the same record hash. It runs in normal CI. The 100-trial runner uses the smaller seeded scenarios below.

`three_node_snapshot_and_process_restart_converges` adds a second replica and the recovery sequence from the SOW §26 demonstration. It waits for both replicas, stops the primary to publish an offline snapshot, kills one replica while the primary keeps writing, and verifies catch-up after restart. It then kills the primary with a write in flight, verifies every acknowledged key and snapshot-plus-WAL replay on restart, and compares the final LSN, history hash, and values in both replica directories. Each seed changes the snapshot, replica-restart, and primary-kill write boundaries. The Docker demonstration and benchmark mixes remain separate checks; this test exercises the failure path with three real processes and local data directories.

Normal CI runs one seed of each smaller scenario. The [100-trial runner](../scripts/run_failure_trials.sh) changes the write boundaries using `DDB_FAILURE_SEED` and runs both scenarios for seeds 0–99. The **Process failure trials** GitHub workflow runs it on pull requests that change source, the test or the runner, and can also be dispatched manually. Its completion is a separate acceptance gate; the presence of the script or workflow alone does not establish that 100 trials have passed. Preserve the failing seed and logs if a trial fails.

On 2026-10-01 UTC, [workflow run 36807500982](https://github.com/aarochu/DistributeDB/actions/runs/36807500982) passed all seeds 0–99 on `ubuntu-24.04` for the current test (pull request #9, merged as `ae255f1`). In each trial the replica was killed while the primary streamed writes and the primary was killed while a client wrote; the restarted primary held every acknowledged key and the replica converged to it. An earlier run, [36807244555](https://github.com/aarochu/DistributeDB/actions/runs/36807244555) at `a682504`, passed an older version of the test that killed processes only between writes and did not check the primary's recovered data. These results apply to the specific process-kill test and runner environment.

The test models process termination. It does not prove that a storage device honors sync after loss of power. The simulated filesystem tests cover separately stated crash and torn-write models. A physical power-cut exercise on the [selected filesystem profile](ADR-001-Language-and-Filesystem.md) would be needed to make a stronger hardware durability claim.
